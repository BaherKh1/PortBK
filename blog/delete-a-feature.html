The feature I deleted and what it saved

2 September 2026 · 3 min read

Pollen had a scheduling toggle. It let a teacher mark Tuesday lessons as "auto-confirm" so students did not have to wait for a manual yes. It sounded useful. In eighteen months, 41 accounts turned it on, 12 kept it on, and 3 could explain what it did.

It also had a cron job that recalculated confirmations every fifteen minutes, a settings page with a warning nobody read, and a support macro that began "If your Tuesday lessons look wrong…". Once a week, someone in the team asked whether we should improve it. That question was the most expensive part.

The audit that made the decision

We looked at three things: usage, support tickets and engineering time. Usage was tiny. The tickets were not. Auto-confirm produced more confused messages per active account than any other setting, because it silently changed what a student saw on a day the teacher had already planned. And the code touched the booking flow, which meant every change to bookings required someone to remember the toggle existed.

The feature was not broken. It was doing exactly what we built. It was just solving a problem most teachers did not have, in a way that made the main flow harder to reason about.

How we removed it without breaking trust

  1. We told the 41 accounts first. A short email, a date, and a one-click link to a manual approval flow that already existed.
  2. We kept the data. The setting stayed in the database, unread, so nobody lost a record of what they had chosen.
  3. We removed the UI and the cron job together. Half a removal is worse than none, because the hidden half keeps generating tickets.
  4. We wrote down why. A one-page note in the repo, linked from the old settings route, so the next person does not rebuild it by accident.

Two accounts wrote back to complain. Both were using it for a workflow we had not imagined, and both were fine once we showed them the manual flow. Nobody churned. The support macro was deleted. The weekly argument stopped.

What it saved

The cron job was cheap in compute and expensive in attention. Every time bookings changed, someone had to check it. Removing it cut a branch out of the flow that had been tested less than the main path. Within a month, the booking screen was simpler to change, and two small improvements that had been stuck behind "but what about auto-confirm?" shipped.

The real saving was not the server cost. It was the end of a conversation we had been having every week for a year. Features do not only take code to build. They take code to keep, explain, support and defend. That cost does not appear on a roadmap, which is why it is so easy to add one more toggle.

The rule I use now

Before shipping a setting, I ask who will turn it on, who will turn it off, and who will answer the message when it behaves strangely. If I cannot name the third person, the setting is not ready. Sometimes the answer is that the feature should be the default instead. Sometimes it is that the feature should not exist.

Deleting is a product skill. It is also the cheapest performance work you can do.
