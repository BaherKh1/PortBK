How a change ships without me in the room

11 November 2026 · 6 min read

Last Tuesday a teacher on Pollen could not change the currency on her checkout page. She had moved from Lisbon to Berlin, her students were paying in the wrong currency, and the error message told her to contact support. I read the ticket at 9:40. By 14:05 the fix was in production and she had a reply. I did not write a line of it.

That is not a magic trick and it is not full autonomy. It is a pipeline with three honest parts: a brief that can be rejected, a build that cannot touch anyone else's work, and a review that somebody other than the author performs. I want to describe one run end to end, including the parts that are still manual, because most writing about agents skips the boring gates that make the whole thing safe.

1. The ticket becomes a brief

Every change starts as a written brief, even when the source is a one-line ticket. The brief has five fields: the problem in the customer's words, the smallest acceptable change, the parts of the system that are allowed to change, the parts that are not, and how we will know it worked. If a field is missing, the brief is rejected and the ticket goes back to me. Rejection is cheap. A vague brief is expensive because every later step inherits the vagueness.

For the currency ticket the brief was short. The problem: a teacher in a new country sees a checkout in her old currency. The smallest change: let the owner pick a currency per page, defaulting to the account currency. Allowed to change: the settings form, the checkout renderer, one database column. Not allowed: pricing rules, payout schedules, anything that moves money. Success: a test account can switch currency, and an existing checkout keeps the currency it was created with.

That last sentence is the important one. "Success" is not "the feature works". It is a thing a stranger can check without asking me what I meant.

2. One agent, one copy of the code

The brief goes to a builder agent with its own checkout of the repository. Parallel jobs never share a working tree, which removes the entire class of problems that comes from two agents editing the same file at the same time. Each run gets a branch, a time limit and a token budget. If it runs out of either, it stops and reports what it has instead of improvising a bigger change.

The builder is allowed to read the whole repository, run the test suite and add tests. It is not allowed to deploy, send email, change billing configuration or merge. Those permissions live outside the agent's reach, in the CI system and in my account, not in a polite instruction inside a prompt. A rule that only exists in a prompt is a suggestion.

The first draft for this ticket came back in eleven minutes with a migration, a form change and four new tests. Two of the tests failed. The agent fixed one and left the other failing with a note: the existing checkout fixture assumed a single currency. That note was correct, and it was the moment I trusted the run.

3. Reviewers who did not write the code

Every pull request gets two reviews from agents that did not write it. One checks correctness: does the diff do what the brief says, do the tests actually test it, is there a path where the old data breaks. The other checks risk: secrets, personal data, money, permissions, and whether anything now runs without a human in the loop.

A review from the author is a proofread. A review from a different agent is a second opinion. They are not the same thing, and only one of them catches a confident mistake.

The correctness reviewer found the real bug in the draft: the new column was added with a default, but the checkout cache was never invalidated, so a teacher would have seen the old currency for up to an hour. That is exactly the kind of thing a builder misses because it is thinking about the happy path it just built.

The risk reviewer had less to do. It confirmed that the migration was additive, that no payout code was touched, and that the new setting was scoped to the account owner. It also flagged that the settings form now had two save buttons, which was ugly but not dangerous. I fixed that myself in four minutes, which felt like a bargain.

4. The gate I keep closed

Nothing merges itself. The pipeline can open a pull request, run the tests, leave two reviews and post a summary in the channel, but the merge button belongs to a human. The same is true for anything that sends a customer email, changes a price, issues a refund or rotates a key. Those actions have a separate approval step that a scheduled job cannot skip, no matter how confident it is.

This is not distrust of the tools. It is a boundary I can explain to a customer. If something goes wrong, there is a person who looked at the change and said yes. That person is me, and I would rather spend ten minutes a day reading diffs than an afternoon explaining an automated refund to someone's finance team.

5. What it actually costs

The run consumed about 40 minutes of machine time and roughly €3 of model usage. My time was 22 minutes: reading the ticket, writing the brief, reading the two reviews and the diff, and writing the reply to the teacher. On a good day this is a four-to-one trade. On a bad day the brief is wrong, the agent builds the wrong thing carefully, and I spend an hour untangling it.

The difference between those days is almost never the model. It is whether the brief described a checkable outcome. When I skip that part, I am not saving time, I am borrowing it at a bad rate.

What I would tell someone starting

  • Write the brief before you open the tool. If you cannot fill five fields, you are not ready to delegate.
  • Give every run its own copy of the code. Shared workspaces turn parallel work into a merge conflict with extra steps.
  • Put permissions in the system, not in the prompt. The agent should be unable to deploy, not asked not to.
  • Make a different agent review the work. Self-review is a proofread.
  • Keep one human gate around money, customers and production. Automate the queue, not the judgement.

The teacher got her currency switcher and a reply that afternoon. I got a diff I understood and a pipeline that will handle the next ticket while I am on a call. That is the whole promise: not that nobody is in the room, but that the person in the room is doing the part that needs a person.
